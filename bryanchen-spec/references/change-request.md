# 变更请求细则（CR：Change Request）

**定位**：spec 进行中，需求要**增 / 改 / 删**时走的正式流程。它是父 spec 的微缩四步，
产物落在 `specs/{父目录}/changes/CR-xx_<slug>.md`，收口时**合入父 spec 正式文本**。

**它治的失效**：边做边改需求变成「聊天记录里的口头变卦」——没有影响面评估、没有已实现代码的
处置交代、没有作废任务的账。spec-kit 官方把这种回改模式的风险直接写成 **silent divergence（静默漂移）**。

**与父 spec 的关系**：CR **不是新 spec**。它产生的 R/T 沿用父 spec 编号序列（`R-06`、`T-09`），
追溯链保持一条：`CR-01 → R-06 → T-09 → commit footer → MILESTONE → CHANGELOG`。

---

## 一、触发与分诊（先分诊，再决定开不开 CR）

触发语：「需求变更」「改需求」「加一条」「R-03 不对/要改」「砍掉 R-05」「范围调整」；
或我在 Implement 中发现**需求本身需要变**（区别于发现代码缺陷）。

**分诊三判据**（决定进哪本账，防三本账互相倒货）：

```
原 spec 描述的行为，是「应该那样」吗？
├─ 是，代码没做到          → bugs.md（BUG-xx），不走 CR
├─ 不是，需求该增/改/删     → CR-xx（本文件）
└─ 有道理，但这次不做       → backlog.md（BL-xx），CR 内不留悬空条目
```

- 分诊由 **agent 提议、用户确认**；争议时（既像缺陷又像变更，例如「spec 写的可实现但代价极高」）
  → 默认按 CR 走（因为它要改文档），并在 CR §S 记「疑似缺陷，BUG-xx 待评」。
- **判据错的代价**：把需求变更记成 bug → 父 spec 文本与现实永久背离；把缺陷记成 CR →
  bugs.md 不完整（列表不完整就没人信）。

---

## 二、三档分级（四步产物一律齐全，只省确认轮次）

| 档 | 判据（任一满足即该档，冲突取高档） | 四步产物 | 确认次数 |
|---|---|---|---|
| `micro` | 纯措辞/参数微调；不新增 R；**不改已有 R 的行为语义**；不影响已合并 commit | §S 必填，§P/§T/§I 各一行 | **1 次**（整份 CR 一次确认） |
| `minor` | 新增 R；或改已有 R 的行为语义；或删 R | 四节齐全 | **2 次**（§S+§P 一次，§T 一次） |
| `major` | 改目标/砍范围/方向推翻；或影响面跨 ≥3 模块；或触及共享面；或涉 SQL/配置变更 | 四节齐全 + 影响面专章 | **3 次**（与父 spec 同规格） |

- **档位由 agent 提议、用户拍板**；**agent 永不自行降档**（不得为省一次确认而降档）。
- 降档需用户明确同意，并写进 changelog：「CR-02 由 major 降 minor（用户同意，原因: …）」。
- 发现措辞改动实际改变了断言 → **强制升 minor** 并报告。

## 三、四步细则

### §S Specify（变更意图 → R 条款增/改/删）

必含六件：

1. **变更来源与触发**：谁、何时、**原话引用一句**（防日后争议「我没说过」）。
2. **三张清单**：`新增 R-xx` / `修改 R-xx（旧文摘要 → 新文）` / `删除 R-xx（原因 + 拍板人）`；
   EARS 句式与父 spec §2 同规格，需求正文禁实现细节。
3. **受影响既有 R 清单（哪怕不改它）——必答**：新增需求会不会与某条既有 R 打架？
   本 skill 实测过「加一条需求破坏另一条，两层自动化都没发现」，这一问是唯一防线。
4. **Non-goals（本次不跟着做的）**：范围蔓延的直接刹车。
5. **「为何不能另立新 spec」一句话**（micro 免）：防把无关需求塞进正在做的事。
6. **假设显式列出** + 结尾「现在纠正，否则按此执行」（复用父 spec 规则）。

门控：确认①' → CR 头写 `§S状态: 已确认 | 确认人: xxx | 日期`。

### §P Plan（影响面 + 已实现处置）★这一步最容易省，也最值钱

1. **影响面矩阵**：触及的模块 / 接口 / 表列 / 配置 / 共享面对象
   （共享面判据复用 §3：「还有谁依赖这个路径/列/配置？」）。
2. **已实现处置表（CR 独有，逐条交代已完成任务）**——四类处置各有后果：

| 处置 | 含义 | 后果（必须写清） |
|---|---|---|
| **保留** | 不受影响 | 无 |
| **改造** | 旧实现需按新语义改 | 新任务承接；旧断言必须同改并复跑 |
| **回退** | 需求作废，旧实现不该存在 | `git revert` 单列 commit（**不删历史**）；tasks 原行标 `[作废 CR-xx]` |
| **拆分** | 旧任务部分仍有效 | 保留有效部分，缺口另立新 T 并注明来源 |

3. **被拒绝的替代方案 + 理由**——其中**必须包含「另立新 spec」这一选项**并说明为何不选
   （这是防蔓延的第二道刹车）。
4. **风险与规避** + **是否需要拆版/换挂版**的判断（见 §五）。

### §T Tasks（增 / 改 / 废 三类任务）

- 新任务续父 spec 编号（`T-09+`），沿用父 spec 五项（描述/关联/依赖/验证方式/验收标准），
  **加两项 CR 专属**：`CR: CR-xx`、`处置: 新增|改造|回退|拆分`。
- **作废任务不删除、不取消勾选**：原样保留并标 `[作废 CR-xx v1.2.0]`——进度是历史事实，
  删了就查不到当时做到哪。
- 自检三条：每条新/改 R 有 T 覆盖？有 T 找不到 R（超范围）？**已合并 commit 是否都出现在
  §P 处置表里**（防「改了但没交代旧代码去哪了」）。

### §I Implement

1. **顺序不可反**：停施工 → 改 CR 文档 → 三份合入（§四）→ 才写码。
2. 执行新 T，一任务一 commit，footer 加 `CR: CR-xx`（与 `Spec:`/`Task:` 并列）。
3. 回退类处置**单独 commit**（`revert:` 型，不与新功能混——git-workflow 红线 4）。
4. 完成后执行**合入八动作**，其登记 commit 是 CR 的封口。

## 四、★合入父 spec 八动作（「纳入整体 spec」的机械步骤）

> 八动作全做完才算 `状态: 已合入`，**缺一即未收口**（审计会抓）。

| # | 动作 | 写在哪 | 规则 |
|---|---|---|---|
| 1 | R 条款落进 requirements.md | 父 `requirements.md` | 新增/替换文本；删除标 `[已删除 v1.2.0 \| CR-01 \| 原因 \| 拍板人]`，**编号永不复用** |
| 2 | 版本 bump + 状态推进 | 父三文档版本头 | 按 §六或 versioning.md §1.6 映射（新增 R→MINOR；删 R/改范围→MAJOR；措辞→PATCH） |
| 3 | changelog 记到编号级 | 父 `changelog.md` | `## v1.2.0（日期）CR-01 确认人: xxx` + 逐条 R/T 变更与回退 commit hash |
| 4 | 任务并入父 tasks.md | 父 `tasks.md` | 新 T 进正常任务区；作废/改造标注落原任务行；CR 区块只留索引 |
| 5 | CR 文件盖合入戳 | `changes/CR-xx_*.md` 头 | `状态: 已合入 → 父 v1.2.0 | 合入日期 | 收口 commit` |
| 6 | MILESTONE 同步 | 挂的 `releases/vX.Y.Z/MILESTONE.md` | 需求表已挂行更新计数；CR 引入 SQL/配置 → 重跑 artifacts.md + **Flyway 补号**（`_03a`，不重排已评审序号） |
| 7 | 关联账联动 | `backlog.md`/`bugs.md`/`lessons.md` | CR 内「本次不做」的意向转 BL；根因是缺陷走 bugs；CR 暴露的流程坑记 L |
| 8 | 合入登记 commit | git | `docs(spec): CR-01 合入 v1.2.0（增 R-06 改 R-02 废 T-03）`——**独立 commit，不与代码混** |

## 五、冲突与现场处置（逐条给规则）

| 情形 | 规则 |
|---|---|
| HEAD 停在 feature/fix 分支 | CR 文档属 spec 文档 → 必须回**账房（版本分支）**写（§1 步骤 0 一票否决照常生效） |
| 同一 spec 已有未收口 CR | **串行不并发**：先报「CR-01 施工中未合入」，处置完才开 CR-02（与「在途版本唯一」同构） |
| 施工中的未完成任务 | 开 CR 即**实现暂停**（除非该任务明确「不受 CR 影响」）；现场如实挂账（「T-05 停在半成品，待 CR-01 §T」）——不允许边改需求边赶进度 |
| 所在版本已冻结（M2 后） | 挤入需用户**明确同意**（解冻重走 M2，changelog 记录）；默认建议：CR 转下一版本，父 spec 标 `CR-02 → v1.5.0` |
| 已 M3 汇总升级件 | CR 涉 SQL/配置 → **M3 必须重做**（补号 + 重排校验 + UPGRADE.md 更新），否则拒绝合入 |
| **已 M4 打 tag** | **禁止 CR**。tag 是历史凭证（同「账不齐不打 tag」逻辑）；要改 → 另立新 spec 挂新版 |
| 已合入版本分支/已 merge 的代码受 CR 影响 | **不回退已进账房的合并**；由 §P 处置表新建改造/回退任务，用**新 commit** 修正，历史不动 |
| CR 引发跨模块大改（>5 文件或 >20 任务） | 触发拆分问句：「本次变更已超出原 spec 容量，建议另立 `fix-xxx`/`add-xxx` spec」——agent 提议、用户裁 |
| CR 期间用户又提新变更 | 同域并入当前 CR；异域串行开 CR-02；**禁止静默追加** |

## 六、状态机与未收口审计

```
父 spec: 草稿 → 三重确认 → Implement → 【变更中 CR-xx】→ Implement → 已合并 →（随版发布）
CR:      草稿 → §S' → §P' → §T' 确认 → 施工中 → 已合入
                                                     └─ 旁路: 已放弃(原因+拍板人) / 转新 spec / 转 BL
```

- **未收口判定**：CR 状态 ∉ {已合入, 已放弃} 即未收口；八动作完成度需能逐项打勾。
- **审计钩子**（三处必查）：
  - 「spec 状态」/「待办同步」/「审计里程碑」→ 增查**未收口 CR 清单**；
  - **合并条件**加一条：本 spec 无未收口 CR（git-workflow §三）；
  - M2 冻结前置检查 + M3 步骤 0 审计：纳入 spec 若有未收口 CR → 硬阻断。

## 七、防滥用（流程得防住它自己助长的东西）

| 机制 | 规则 |
|---|---|
| **CR 数量刹车** | 同一 spec 累计 **≥3 个 CR** → 强制反思问句：「是当初 §Specify 没做好，还是这事本该拆多个 spec？」agent 建议、用户裁；**只出话不阻断** |
| **范围自检问句** | §S 末尾固定一行：「本 CR 是否让本 spec 的可交付目标发生变化？是/否 + 一句」；答「是」→ 升 major 并触发拆版问句 |
| **micro 不可滥用** | micro 判据是「不改行为语义」；一旦改变断言即强制升 minor |
| **CR 不继承父确认** | CR 产生的新 R 必须走 CR 自己的确认门，**不能因为「父 spec 已确认」就跳过** |
| **MAJOR 不强制全量重确认** | 但 §P 必须给「其余 R 未受影响」的**逐条声明** + 用户一句认可；两者缺一按全量重确认处理 |

## 八、口令速查

| 用户说 | 动作 |
|---|---|
| 需求变更 / 改需求 / 加一条 / 砍掉 R-xx | 分诊（§一）→ 提议档位 → 开 CR |
| 变更列表 / 有哪些 CR | 只读回显各 spec 的 CR 与状态（含未收口） |
| 继续 CR-01 | 定位 CR 当前步骤续做（先验 HEAD 在账房） |
| 放弃 CR-01 | 必须用户给原因 + 拍板人，agent 不得自行放弃 |
| 合入 CR-01 | 执行 §四八动作（逐条回执） |

## 九、与现有机制的关系

| 机制 | 关系 |
|---|---|
| 铁律 4（确认后改内容=作废） | CR 是它的**正式通道**：走 CR 的改动天然带重确认；不走 CR 的擅自改动仍按作废处理 |
| 铁律 6（发现问题就停） | 发现**代码缺陷**→bugs；发现**需求缺陷**→CR；两者都在停施工之后处理 |
| 生产代码保护（铁律 3） | CR 的 §S~§T 期间同样生效：只许写 `changes/`，禁改源码 |
| versioning.md | CR 触发父 spec 版本 bump；映射表见 versioning.md §1.6 |
| milestone.md | 冻结/已汇总/已 tag 三种状态下 CR 的约束不同（§五）；CR 引入升级件走 Flyway 补号 |
| bugs.md / backlog.md / lessons.md | 分诊三判据（§一）；CR 内「不做」的意向必转 BL，不留悬空 CR |
| git-workflow.md | footer 增 `CR:`；合入登记独立 commit；回退单独 commit 不删历史 |
