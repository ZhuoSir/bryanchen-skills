# Bug 管理细则（bugs.md）

项目级唯一清单：`specs/_project/bugs.md`（与 profile.md 并列，init 时创建空表，之后持续维护）。
bug 跨 spec 跨版本，所以不属于任何单个 spec 目录；列表不完整就没人信，所以**登记是义务**。

---

## 一、编号与字段

> **台账边界**：本表只记产品缺陷（代码行为与承诺不符）。过程/工具/环境/判断类跟头
> （含误判、假阳性、白折腾）进 `specs/_project/lessons.md`；因坑致缺陷时两边互引（BUG 行注 L-xx）；新需求意向进 backlog.md（BL-xx）——缺陷延期走本表「待挂版/已延期」，不进 BL。
>
> **分诊判据（BUG vs CR vs BL，三本账不得互相倒货）**：问「原 spec 描述的行为，是*应该那样*吗？」
> ——**是，代码没做到 = BUG（本表）**；**不是，需求本身该增/改/删 = CR**（`references/change-request.md`，
> SKILL.md §13）；**有道理但这次不做 = BL**（backlog.md）。
> 把需求变更记成 bug 的代价：父 spec 文本与现实永久背离；把缺陷记成 CR 的代价：本表不完整。
> 争议时（「可实现但代价极高」）默认按 CR 走（它要改文档），并在 CR §S 记「疑似缺陷，BUG-xx 待评」。

- 编号 `BUG-01` 起，**永久不复用**（同 R/T 规则；作废的编号标 `[作废]` 保留）。
- 每条固定字段：

| 字段 | 说明 |
|---|---|
| 编号 | BUG-xx |
| 标题 | 一句话现象，可判定（❌「登录有问题」✅「登录页空密码提交导致 500」） |
| 严重度 | P0 阻断/资损 · P1 核心功能错误 · P2 一般缺陷 · P3 体验/瑕疵 |
| 发现于 | 来源场景+日期：`生产(2026-09-20)` / `spec Implement中(<目录> T-02)` / `对话中(09-28)` / `M4演练` / `init体检` |
| 状态 | 见状态机，**必须带版本** |
| 修复版本 | 计划或实际的 vX.Y.Z；未规划则「-」 |
| 关联 | Spec:/Bug 引发的 spec/commit hash，可选 |

## 二、状态机（状态与版本对应）

```
新建 ──→ 已规划(vX.Y.Z) ──→ 已修复(vX.Y.Z) ──→ 已验证(vX.Y.Z) ──→ 已发布(vX.Y.Z)
  │
  ├─→ 已延期(从vA→vB)：必须写从哪移到哪 + 原因，等移
  └─→ 不修复(原因 + 批准人)：⚠️ 必须用户批准，agent 不得自行决定也不得补批准人
```

- **已规划(vX.Y.Z)**：纳入某里程碑修复（在 MILESTONE.md 挂 bug 行或用户口头指定）
- **已修复(v1.3.0)**：fix 已合并进对应分支，将随 v1.3.0 出去——commit footer `Bug: BUG-xx` 是其证据
- **已验证(v1.3.0)**：复现步骤重跑不通过（贴输出）；验证人=用户或其明确委托
- **已发布(v1.2.1)**：已随版本上线（由 M4 批量翻转，翻转日期记入状态）
- 已修复但发版前该版本砍了 bug → 回退为「已延期/改规划到下一版本」，**不许静默漂移**

## 三、登记触发（何时写入，对应 SKILL.md §5 义务表）

| 场景 | 时机 | 注意 |
|---|---|---|
| Implement/体检中发现既有代码 bug | 发现即登记 | 不顺手修（除非阻塞本需求）；若因它阻塞 → 登记后立即可规划进当前版本 |
| 对话中用户提到异常 | 立即登记（状态「新建」，严重度可「待评」） | 哪怕后来发现不是 bug → 状态标「不修复(原因: 非缺陷，是…+批准人)」留痕 |
| 直接修掉的小 bug（NOT for 快速路径） | **修完强制补登记** | 一行流水账；状态直接落「已修复(vX.Y.Z)」 |
| M4 演练发现 | 登记 | P0/P1 阻塞发布 → release 分支内修，规划挂本版本 |
| 自己实现中验证不过 | 不登记 | 那是任务未完成 → completion.md，混淆会把列表变脏 |
| **需求本身**要增/改/删（代码没做错，是要改承诺） | **不登记** | 走 CR（SKILL.md §13）；误记会把 spec 变更藏进缺陷账 |

## 四、修复分级

**小 bug（原因明确、单点、有验证方式）**：
1. 用户说「修 BUG-xx」→ 建轻量任务直接修（不走四阶段，不需 spec 目录）
2. 修复 → 复现步骤重验贴输出 → commit footer `Bug: BUG-xx`（无 Spec footer 也合法）
3. 翻状态「已修复」；有里程碑归属时挂进对应 release

**回归的法定定义**（一切修复的「回归」以此为准，含上面第 2 步与大 bug 单）：
- 回归 = 复现证据转绿 **+（若缺陷位于共享命名空间）该命名空间全部身份的探针回归**
  —— 判据与身份矩阵见 SKILL.md §3；只验缺陷自身不验对面身份 = 未回归
  （教训原型：修登出跳转豁免 GET 打死 POST 登录 API，半天后才由用户现场发现）
- **回归载体 = 项目指定的自动化断言套件**（verify 脚本、测试套件等；项目没有时，
  由触碰共享面的这单在 plan 中立项建立并入库）——合并/提交前跑全量并贴 exit code；
  build / 类型检查通过**不算**回归证据

**大 bug（跨模块、或根因是需求缺陷）**：
1. 升级建 spec：`specs/{日期}_fix-{描述}/`，requirements 里 `关联: BUG-xx`
2. 完整四阶段+三重确认照常；合并/发版时 BUG-xx 状态跟着版本走
3. 判断标准模糊时问用户一句，不自行降级

## 五、与里程碑的联动（对应 references/milestone.md）

- **M1 / 处置问句**：登记后或用户说「修 BUG-xx」时问一句挂法——
  「挂当前在途版（进本版缺陷表）/ 待挂版（攒纯修复批发 c 版）/ 不修复(你批准)」；
  选定后状态翻「已规划(vX.Y.Z)」+ 对应 MILESTONE.md 缺陷表加行
- **M2 冻结前置**：本里程碑已规划中 **P0/P1 全部达「已验证」**才许冻结
- **M3 汇总**：RELEASE-NOTES.md 的「## 修复」节从 bugs.md 过滤「修复版本=本版本」生成，不靠回忆
- **M4 发布**：**三步对账**（收网/翻账/反核+报尾，见下），不是单列翻转
- **M2 冻结**：账证初对——本版分支已合并提交的 `Bug:` footer ⊆ 台账行且状态 ≥ 已修复

### 回退处置（仅用户口令「回退 vX.Y.Z」触发；agent 永不主动提议）

固定问句二选一：
```
「vX.Y.Z 回退两条路：
  a) 向前修复（推荐）：缺陷记 BUG-xx（发现于: 发版后，根因 vX.Y.Z）→ 正常修复流程 → 发 v<X.Y.Z+1>
  b) 整版撤回：先列该版带入的提交清单（git log <上一tag>..vX.Y.Z --oneline --no-merges）给你过目
     → 按 versioning.md §2.5 四纪律执行：逐提交 revert(Rollback: footer) + rollback SQL 逆序
     + config 反 apply + 台账「已撤回」+ CHANGELOG 标注 → 发 v<X.Y.Z+2>」
选 a / b / 先看清单。」
```

### 发版对账三步法（M4 强制）

```bash
# a) 收网：本版实际带出的修复，以 footer 为硬锚
git log <上一tag>..X.Y.Z --grep "Bug:" --format="%h %(trailers:key=Bug,valueonly)"
#    → 出现的每个 BUG-xx 核台账：缺登补登、状态如实回填

# b) 翻账：本版「已验证/已修复」→「已发布(vX.Y.Z)+日期」

# c) 反核：台账写「修复版本=本版」的每一行，其修复提交须满足
git merge-base --is-ancestor <修复commit> X.Y.Z    # 假 = 没随版，状态撤回并标注
#    收尾打印「未随本版清单」（已规划vNext/待挂版），用户确认去向才算完成
# c2) 回退核（若台账存在「已撤回」版）：被撤版每个提交须有对应 Rollback: footer
#     （或被后续版重新带入）；缺口 = 半回退，阻断发版
```

**为什么三步缺一不可**（治三种真实漂移）：修了没记（a 收网治）、
记了没翻（b 翻账治）、翻了没随版/根本不在本版范围（c 反核治）。
footer 是账证勾稽的唯一硬锚——所以修 bug 的 commit 带 `Bug:` 是红线级要求。

## 六、bugs.md 文件格式

见 templates.md 「specs/_project/bugs.md」模板；表格式单文件，历史版本条目不删除
（已发布行永远保留，列表即审计记录）；定期由 init 刷新时只校对不重写。
