# 产物模板（四个文件 + .specrc.yml）

创建 `specs/{YYYYMMDD}_{功能名}/` 时按以下模板初始化。`<>` 为占位说明，落盘时替换或删除。

---

## .specrc.yml（项目根，Phase 0 首次探测后经用户确认写入）

```yaml
# .specrc.yml —— bryanchen-spec 规范源路由表（团队共享，进 git）
# 源取值: global | file:<相对路径> | skill:<skill名> | none
domains:
  code-backend:   <global|file:...|skill:...|none>
  code-frontend:  <...>
  api-design:     <...>
  database:       <...>
  git-workflow:   global
  versioning:     global
project_files:
  - AGENTS.md      # 存在才列；永远生效，优先级最高
```

## requirements.md

```markdown
> 版本: v0.1.0 | 状态: 草稿 | 更新: <YYYY-MM-DD>

# 需求规格：<功能名>

## 背景与目标
<为什么做；解决谁的什么问题；成功长什么样（可度量的结果）>

## 需求条款

### R-01 <需求短标题>
<WHEN/IF/WHERE/WHILE 触发条件>,
系统 SHALL <可观察行为>。
<补充约束：量化指标、边界值。不写实现细节。>

#### 验收场景
- **GIVEN** <前置状态>
  **WHEN** <操作/事件>
  **THEN** <可观察结果>
- **GIVEN** <异常/边界前置>
  **WHEN** <操作>
  **THEN** <结果>

### R-02 ...

## Non-goals（范围外）
- <明确不做什么，防范围蔓延>

## 我正在做的假设
1. <假设内容>（如不成立请现在指出，否则按此执行）
2. ...

## 待确认问题
- <阻塞性问题列这里并停住等答复；没有则写「无」>
```

## plan.md

```markdown
> 版本: v0.1.0 | 状态: 草稿 | 更新: <YYYY-MM-DD>

# 技术方案：<功能名>

## 方案概述
<采用什么方案，一段话；对应满足哪些 R-xx>

## 涉及模块与数据流
<改动哪些模块/服务；关键数据流或时序（可用 ASCII 图）>

## 接口设计
<新增/修改的接口：方法 路径 入参DTO 出参VO 错误码。遵守 standards/api-design.md>

## 数据模型变更
<新表/改表：DDL 草案 + 索引 + 迁移与回滚。遵守 standards/database-design.md。无则写「无」>

## 共享面身份矩阵（触碰共享面时必填，判据见 SKILL.md §3）
<!-- 「还有谁依赖这个路径/列/配置？」有一个以上"是"即为共享面。
     每个既有身份一行；本表就是 Tasks 断言与提交对面证据的清单源 -->
| 对象 | 身份（方法×调用方×端点） | 变更后预期行为 | 断言归属任务 |
|---|---|---|---|
| 示例：/auth/login 路由 | GET = SPA 页导航 | 返回 index.html | T-0x |
| 示例：同上 | POST = 登录 API | 返回 JSON 信封 | T-0x |

## 关键决策
### 决策 1：<标题>
- 采用：<方案> 理由：<为什么>
- 被拒绝：<替代方案A> 理由：<为什么不>；重新评估条件：<何时值得重看>

## 风险与规避
- [风险] → 规避方式

## 依赖与前置
<依赖的其他模块/接口/配置；无则写「无」>
```

## UPGRADE.md（releases/vX.Y.Z/，M3 编写）

```markdown
# vX.Y.Z 升级操作手册

## 升级前
- 备份：<数据库备份命令/快照要求>
- 确认：<当前版本 ≥ vX.Y.(Z-1)？磁盘/窗口期？>
- 通知：<停机与否、影响时段>

## 升级步骤（严格按序）
1. 停服/摘流量（如需）：<命令>
2. 部署制品：<服务清单与顺序（被依赖方先）、版本>
3. 执行 SQL（按序号序，逐个确认输出）：
   - sql/V<版本>_01__xxx.sql → 预期: <影响行数/无报错>
   - sql/V<版本>_02__xxx.sql → 预期: ...
4. 应用配置（对照 config/changes.md 逐条）：
   - <dataId/文件>: <key> = <新值>（热更/需重启）
5. 启服/挂流量
6. 验证：
   - <核心功能验证步骤与预期结果，逐条可勾选>

## 回滚步骤（逆序）
1. 停服/摘流量
2. 回滚配置：<逆序恢复旧值>
3. 执行 sql/rollback/R<版本>_NN__xxx.sql（逆序号序）
4. 回退制品至 <上一版本>
5. 验证回滚后核心功能

## 注意事项
- <不可重入 SQL 的位置与执行纪律；大表 DDL 的低峰要求>
```

## checklist.md（releases/vX.Y.Z/，M4 前人工勾选）

```markdown
# vX.Y.Z 发版检查单

## 产物完整性
- [ ] sql/ 文件数 = MILESTONE.md 登记数，rollback 一一配对
- [ ] 每个 SQL 文件头注释块完整（版本/序号/来源/可重入/回滚）
- [ ] config/changes.md 覆盖全部配置项（与各 spec artifacts.md 核对）
- [ ] RELEASE-NOTES.md / UPGRADE.md 已评审
- [ ] **变更↔断言配对表**：本版每个触碰共享面的变更，项目回归载体
      （verify 脚本/测试套件）有对应新或改断言，逐变更列断言编号；
      无配对 = M4 不过（防「新规则没配新断言，旧行为悄悄死掉」）

## 演练（必须真做，不许纸面勾选）
- [ ] 演练环境按 UPGRADE.md 完整走一遍：SQL 全执行、配置全应用
- [ ] 演练后核心功能验证通过（记录验证人与时间）
- [ ] 演练中回滚步骤也走过一次
- [ ] 演练发现的问题已修复并更新 UPGRADE.md

## 发布
- [ ] **Bug 台账三步对账完成**（bugs.md §五）：本版 `Bug:` footer 与台账互核无差、
      状态全部翻「已发布(vX.Y.Z)」、merge-base 反核通过、「未随本版清单」已报并确认去向
- [ ] 全部 spec 已合并版本分支，CI 绿（发版合 main 按 M4 问句另行确认）
- [ ] git tag -a vX.Y.Z 已打（message 含 spec 清单）
- [ ] 项目根 CHANGELOG.md 已追加本版本条目
- [ ] releases/vX.Y.Z/ 已随 tag 进 main
```
