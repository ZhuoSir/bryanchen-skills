# 产物模板（四个文件 + .specrc.yml）

创建 `specs/{YYYYMMDD}_{功能名}/` 时按以下模板初始化。`<>` 为占位说明，落盘时替换或删除。

---

## .specrc.yml（项目根，Phase 0 首次探测后经用户确认写入）

```yaml
# .specrc.yml —— bryanchen-spec 规范源路由表（团队共享，进 git）
# 源取值: global | file:<相对路径> | skill:<skill名> | none
domains:
  code-backend:   <global|file:...|skill:...|none>
  code-frontend:  <...>
  api-design:     <...>
  database:       <...>
  git-workflow:   global
  versioning:     global
project_files:
  - AGENTS.md      # 存在才列；永远生效，优先级最高
```

## requirements.md

```markdown
> 版本: v0.1.0 | 状态: 草稿 | 更新: <YYYY-MM-DD>

# 需求规格：<功能名>

## 背景与目标
<为什么做；解决谁的什么问题；成功长什么样（可度量的结果）>

## 需求条款

### R-01 <需求短标题>
<WHEN/IF/WHERE/WHILE 触发条件>,
系统 SHALL <可观察行为>。
<补充约束：量化指标、边界值。不写实现细节。>

#### 验收场景
- **GIVEN** <前置状态>
  **WHEN** <操作/事件>
  **THEN** <可观察结果>
- **GIVEN** <异常/边界前置>
  **WHEN** <操作>
  **THEN** <结果>

### R-02 ...

## Non-goals（范围外）
- <明确不做什么，防范围蔓延>

## 我正在做的假设
1. <假设内容>（如不成立请现在指出，否则按此执行）
2. ...

## 待确认问题
- <阻塞性问题列这里并停住等答复；没有则写「无」>
```

## plan.md

```markdown
> 版本: v0.1.0 | 状态: 草稿 | 更新: <YYYY-MM-DD>

# 技术方案：<功能名>

## 方案概述
<采用什么方案，一段话；对应满足哪些 R-xx>

## 涉及模块与数据流
<改动哪些模块/服务；关键数据流或时序（可用 ASCII 图）>

## 接口设计
<新增/修改的接口：方法 路径 入参DTO 出参VO 错误码。遵守 standards/api-design.md>

## 数据模型变更
<新表/改表：DDL 草案 + 索引 + 迁移与回滚。遵守 standards/database-design.md。无则写「无」>

## 关键决策
### 决策 1：<标题>
- 采用：<方案> 理由：<为什么>
- 被拒绝：<替代方案A> 理由：<为什么不>；重新评估条件：<何时值得重看>

## 风险与规避
- [风险] → 规避方式

## 依赖与前置
<依赖的其他模块/接口/配置；无则写「无」>
```

## tasks.md

```markdown

# 任务清单：<功能名>

## 1. <分组名，如 基础>

- [ ] T-01 <动词开头的具体描述>
  关联: R-01
  依赖: 无
  验证方式: <单测/接口测试/命令，写明断言什么。lint/build 只能兜底>
  验收标准: <可判定的完成条件>

## 2. <分组名，如 核心逻辑>

- [ ] T-02 <描述>
  关联: R-01
  依赖: T-01
  验证方式: <...>
  验收标准: <...>

## 3. 验证收尾

- [ ] T-0N 全量回归（验证方式: 项目测试命令全绿，贴输出；规范扫描红线清零）

<!-- 纪律：编号只指向更小编号；每条 R 至少被一个 T 覆盖；禁占位任务；总数 3~20 -->
```
