# 接口设计规范（RESTful / 通用底线）

Plan 与 Implement 阶段涉及接口设计时加载。项目有专属接口规范（如 code-standards 的 02-api-design）时以项目为准。

## 一、URL 与方法

1. 资源用**名词复数**、`kebab-case`、层级 ≤2：
   ✅ `/api/v1/users` `/api/v1/users/{id}/orders` ❌ `/api/getUserList` `/api/user/order/query`
2. 动作靠 HTTP 方法表达：

| 方法 | 语义 | 幂等 |
|---|---|---|
| GET | 查询，无副作用 | ✅ |
| POST | 创建 / 复杂查询（明确约定时） | ❌ |
| PUT | 全量更新 | ✅ |
| PATCH | 部分更新 | ❌（需自行保证） |
| DELETE | 删除（逻辑删也是 DELETE） | ✅ |

3. 非 CRUD 的动作型端点用「资源 + 动作子资源」：`POST /orders/{id}/cancel`，不造 `/cancelOrder`。
4. 接口版本：URI 前缀 `/api/v1/`（全项目统一一种策略）；**破坏性变更必须升版本**，旧版本给出弃用期。

## 二、响应与错误

5. 统一响应包装（全项目一种信封）：
   ```json
   { "code": 0, "msg": "ok", "data": { } }
   ```
   列表：`data: { rows: [...], total: 123 }` 或项目既有 TableDataInfo 结构，不混用两套。
6. 错误码分段：`0` 成功；通用错误 `1xxxx`（参数/认证/权限/限流）；模块错误 `2xxxx` 起每模块一段。
   错误码表集中维护（常量类/枚举），不散落硬编码。
7. msg 人类可读、可直接展示给用户；**不泄漏堆栈/SQL/内部路径**；排查细节进日志（带 traceId），不进响应。
8. HTTP 状态码与业务 code 的分工按项目既有约定统一（如网关层用 HTTP 状态、业务层 code），不各写各的。

## 三、入参与校验

9. **服务端必须校验一切入参**（不信任前端）：required/类型/长度/范围/格式，用声明式校验
   （`@Validated` + `@NotNull/@Size/@Pattern`），校验失败返回统一的参数错误码 + 具体字段信息。
10. 入参 `XxxDTO`、出参 `XxxVO`，**禁裸 Map/Object**（同后端红线 R2）；VO 只暴露需要的字段
    （密码、内部状态、删除标记不出现在任何 VO）。
11. 分页参数统一：`pageNum`（从 1 起）+ `pageSize`（默认 10，**上限 500** 防拖库）；排序字段白名单校验（防注入）。
12. 时间参数/返回统一格式（ISO 8601 `yyyy-MM-dd'T'HH:mm:ss` 或项目约定的 `yyyy-MM-dd HH:mm:ss`，全项目一种）。

## 四、安全与健壮

13. 鉴权在网关/拦截器统一做，接口层只声明权限要求（注解/配置）；**每个接口默认需要鉴权**，公开接口显式声明并评审。
14. 越权防护：按 id 操作资源时校验归属（这个订单是不是当前用户的），不只校验登录态。
15. 写接口考虑**幂等**：创建类用业务唯一键（uk 兜底）或幂等 token；回调类接口必须幂等（重试是常态）。
16. 文件上传：类型白名单 + 大小上限 + 存储路径不可预测（UUID）+ 返回访问 URL 不返回物理路径。
17. 限流：公开接口与高频接口配置限流策略（网关或注解），阈值进配置中心。

## 五、文档与协作

18. 接口文档与代码同步生成（Swagger/SpringDoc 注解齐全：summary、参数说明、响应示例），
    **无文档的接口视为未完成**。
19. 前后端联调前接口契约先定（路径/入参/出参/错误码），契约变更必须通知到前端并更新文档；
    spec 流程下契约变更 = spec 变更，走版本 bump + 重确认。
20. 服务间调用（Feign 等）：契约定义在共享 API 模块，超时/重试/降级显式配置，
    调用结果判断用框架语义（`R.isSuccess`），不裸拆 data。
