# bryanchen-spec —— 四阶段规格开发流程

需求 → 方案 → 任务 → 实现，每阶段产物落盘、人工确认后才推进。
**核心信条：没有三重确认，不写一行生产代码；没有验证证据，不声称完成。**

## 0. 铁律（优先级最高，与其他条款冲突时以本节为准）

0. **引擎互斥（启动步骤 0）**：读项目 `.specrc.yml`——`spec_engine` 已声明且
   ≠ `bryanchen-spec-parallel` → **拒执**并提示改用声明的版本；**缺声明不拒执**
   （视为本版本继续，兼容存量项目，运行时可补写）。
1. **三重确认门**：requirements.md、plan.md、tasks.md 三份文档的版本头必须全部为
   `状态: 已确认` 且确认人非空，才允许进入 Implement。缺任何一份 → 明确告知缺哪份，停住。
2. **agent 不得代确认**：确认人名字必须由用户给出；只有用户明确说「确认/通过/OK」才可写入。
3. **生产代码保护**：三重确认之前，只允许写 `specs/` 下的文档，禁止创建/修改任何源码文件、
   禁止升级依赖、禁止改 CI/构建配置。
4. **确认后改内容 = 确认作废**：已确认文档被修改后，版本头改回 `状态: 待重确认`，
   版本按规则 bump，须重新走确认。
5. **诚实性**：不得声称「测试通过/验证通过/完成」除非贴出真实命令输出。
   lint/build 通过只是兜底，不是行为验证。无法验证时明说原因。
6. **中途发现问题就停**：Implement 期间发现需求/设计缺陷 → 停止编码 → 回改对应文档 →
   版本 bump → 重新确认 → 再继续。禁止「先写了再说」。
7. **铁律不受规范源覆盖**：本节是流程纪律，不是技术规范。任何项目规范
   （AGENTS.md、规范类 skill、.specrc.yml 声明的源）都不得豁免 1~6 条。
   技术规范冲突按 .specrc.yml 路由裁决（见 §8），流程纪律没有裁决空间。
8. **表格闸（产物级质量门）**：每次生成或改动 markdown 产物（spec 三文档、changelog、
   MILESTONE/SHARED/各台账表）后、**回验必跑** `python3 <本skill目录>/scripts/mdtable_check.py <改过的文件>`
   ——退出码 0 才算这次写入完成。表格错乱 = 产物缺陷（与代码不编译同级）：拦的是
   列数不齐／行尾缺 `|`（单元格竖线未转义）／fence 断块／表紧跟正文段落。
   无 python3 时逐行人工数列替代，并在 changelog 注明「表检降级人工」。

## 1. 触发与初始化（Phase 0）

用户消息含「新需求 / 新功能 / 开始做 / 开发功能 / 需求开发」等意图时启动。

1. 从需求提炼功能名（小写连字符，如 `add-member-discount`）；提炼不出或需求太模糊 → 先追问，不臆测。
2. 检查 `specs/` 下是否已有同名/同主题目录：
   - 有 → 问用户是「继续做」（走 §7 续传）还是「新建」（换名或确认覆盖）。

3. **版本归属问（每个 spec 必问一次；agent 不得代选、不得静默挂版）**：
   - 读版本台账 `specs/_project/version.md`。没有台账 = 项目未接入 → 先引导跑
     `spec init`（init 按「git 最高 tag → 构建物版本字段（去 -SNAPSHOT/-dev）→ 新工程 v1.0.0」
     读数写台账；新工程同时自动建 `releases/v1.0.0/` + MILESTONE.md）。
   - **有在途版本** → 先对该版**自动跑里程碑审计**（挂接+进度双向，milestone §五附；
     假勾/漏挂先当面处置再谈新挂），然后问（措辞含现状与建议号）：
     「新需求「<功能名>」挂哪个版本？当前在途 vX.Y.Z（已挂 N 需求/M 缺陷）；
     要新开的话按内容性质建议 vA.B.C。回「挂 X.Y.Z」/「新开」/任意号。」
   - **无在途版本**（上一版已发版）→ 问：
     「vX.Y.Z 已于 <日期> 发版，本需求起下一个版本，建议 vA.B.C（<理由>）。确认或给号。」
   - 用户选「挂当前」→ 本 spec 碎片写「挂接意图: → vX.Y.Z」（主账不直改——
     碎片化全程化，parallel.md §二；此前 v8.x 时代的直写 MILESTONE 行为废止）
   - 用户选「新开」或给号 → 碎片写「挂接意图 + 新版意图（含基点）」→ 随即**抢账房锁落账批**：
     建 `releases/v{号}/` 台账目录 + 裸号版本分支 `{号}`（基点：上一版已合 main→main，
     悬空→悬空 tip 链式切）+ MILESTONE/spec 行 + changelog「挂载:」行 + 台账翻「在途」，
     一次锁内完成（编辑+提交，禁 add -A）。
   - **全局编号一律落账时分配**：启动/实现期发现的缺陷与坑只有候选名（碎片），
     BL/BUG/L 转正号出自串行落账——并行撞号结构性不可能。
   - **未获用户明确选择不建目录不建分支不落账**（铁律）。
   - **版本分支基点（防丢代码）**：上一版已合 main → 从 main 切；上一版**悬空**（已 tag 未合
     main）→ 从该悬空分支 tip 链式切、台账记「基于」；细则 git-workflow §一。
   - **在途唯一 + 悬空拦截**：台账至多一个在途版；存在悬空账或未收口在途 spec 时，问句第一句
     先报账，处置（合 main/迁移挂接/留场/放弃）完才建新版——防静默跳版丢内容。
   - **空间凭证随挂接落账发放（必须早于任何写码）**：账房在落账批为 spec 划段
     （errno/SQL 序号/schema/端口/测试键 → SHARED「命名空间」节）；写码只准用段内值。
     同一落账批记录权威副本**指纹基线**（勾选归一化规则见 parallel.md §2.5）。
   - 定号规则 v a.b.c（a 大版/b 需求迭代/c 修 bug，升位低位归零；**c 版=新号=新分支**）
     见 standards/versioning.md §二。

4. 创建目录与四个文件（模板见 `references/templates.md`）：

```
specs/{YYYYMMDD}_{功能名}/
├── requirements.md    版本头 v0.1.0 | 状态: 草稿
├── plan.md            版本头 v0.1.0 | 状态: 草稿
├── tasks.md           版本头 v0.1.0 | 状态: 草稿
├── changelog.md       记录 v0.1.0 创建 + 「挂载: vX.Y.Z（<日期>，用户确认）」
└──（后续产物）completion.md / artifacts.md 由 §5 收尾生成
```

5. **规范源解析（仅项目首次触发时执行一次）**：
   - 项目根已有 `.specrc.yml` → 直接读取使用，**不再探测、不再询问**。
   - 没有 → 按 `references/standards-routing.md` 的探测顺序生成草稿
     （探测项目 AGENTS.md / docs/conventions/ / catalog 里的规范类 skill / 技术栈），
     展示给用户确认（可改任何一行）→ 写入项目根 `.specrc.yml` → 建议提交进 git（团队共享）。
   - 之后所有阶段加载规范时，一律按此表路由，不再自行猜测。

6. 输出启动摘要：功能名、目录路径、**挂载版本**、**兄弟清单（`git worktree list` 实况 +
   fragments 目录在途数 + 各自涉及模块一行）**、**账房锁状态（持有者/空闲）**、**未落账碎片数**、
规范源一行、**本 spec 工作目录预告（`<父目录>/wt-<功能名>`）**、「进入 Phase 1: Specify」。

## 2. Phase 1 — Specify（requirements.md）

写之前先做：读 `specs/_project/profile.md`（项目画像，存在时必读——技术栈/命令/既有约定/技术债/测试基线都在里面）、项目 README/AGENTS.md、看相关模块现状，不要求用户重复可查证的事实。profile 与现实不符时顺手更新 profile 并在回复中说明（不算 spec 变更）。

内容要求（完整模板见 references/templates.md）：
- **背景与目标**：为什么做，成功长什么样
- **需求条款**：`R-01` 起编号，**编号永久不复用**（删除标 `[已删除 vX.Y.Z]`）
- **EARS 句式**（强制）：`WHEN/IF/WHERE/WHILE <触发条件>, 系统 SHALL <可观察行为>`
  - ❌「系统应该很快」 ✅「WHEN 发起查询请求, 系统 SHALL 在 95% 的请求中于 500ms 内返回」
  - 需求只写「做什么」，禁止实现细节（库名/框架/算法参数 → 留给 plan.md）
- **验收场景**：每条 R 至少 1 个场景（GIVEN/WHEN/THEN），重要需求覆盖正常 + 异常/边界
- **Non-goals（范围外）**：明确不做什么，与做什么同等重要
- **假设显式列出**：`## 我正在做的假设` 一节逐条列出，结尾写「现在纠正，否则按此执行」
- **待确认问题**：阻塞性问题列在回复末尾「需确认后再继续」；非阻塞的记为假设

**门控**：展示全文 → 等用户回复「确认」→ 版本头改
`v1.0.0 | 状态: 已确认 | 确认人: <用户给的名字> | 确认日期: <今天>` → changelog 追加确认记录 → 进入 Phase 2。

## 3. Phase 2 — Plan（plan.md）

**先加载三样**：① `specs/_project/lessons.md` 全部 **active 坑**（项目踩坑台账，制定方案强制参考，见下"坑核对"）；② 按 `.specrc.yml` 路由加载规范：涉及接口 → `api-design` 领域声明源，涉及库表 → `database` 领域声明源（§8）；③ profile 技术债节。

内容要求：
- **坑核对（必备节，置于方案概述前）**：逐条过 active 坑后写——相交的 L-xx 列「本方案如何避开」；
  无相交也必须写「已核对 N 条 active 坑，无相交」——**沉默 = 未核对，确认②不放行**
  （坑被核对过但方案仍踩，回炉该坑的"防再犯规则"）
- 采用方案 + 选择理由
- 涉及模块、数据流、接口与数据模型概要（遵守上述规范）
- **共享面身份矩阵（触碰共享面时的必备节）**：共享面判据——开放式清单
  （nginx/网关/路由路径/DB 共享列/依赖版本/全局配置/共享组件），配一个自检问句：
  **「还有谁依赖这个路径/列/配置？」有一个以上"是"即为共享面。**
  是共享面则必须先枚举该对象全部既有身份（方法 × 调用方 × 端点/版本），
  逐身份写「变更后预期行为」——**矩阵没列的身份 = 未评估**；
  Tasks 的断言与提交的面证据都以本矩阵为源
  （教训原型：/auth/login 的 GET=SPA 页 × POST=登录 API 双身份，豁免只验 GET 打死 POST）
- **被拒绝的替代方案 + 拒绝理由**（每个关键决策必须有，防默默选了烂方案）
- 风险与规避
- 不复制 requirements 内容，只写 how

**门控**：同 Phase 1（确认② → 落盘 → 进 Phase 3）；展示时坑核对节置顶提醒审阅人核这一节。
确认②呈报前两个硬动作：① 有并行兄弟时**跑预检脚本**（对象 ∩ / 空间段 ∩ / 枚举 value diff，
输出附呈报；≠∅ 未仲裁 → 不放行，parallel.md §三）；② 命中评审条件（≥2 共享面/动钱权限/
≥8 任务）→ 附**独立 fresh-context 评审报告**（reviewer 只出清单，裁定权在人）。

## 4. Phase 3 — Tasks（tasks.md）

**先加载规范**：`standards/versioning.md` 的编号规则节。

内容要求：
- `T-01` 起编号，按组划分（如 1.基础 / 2.核心 / 3.接入），编号永久不复用
- 每个任务必含五项：
  ```
  - [ ] T-03 <动词开头的具体描述>
    关联: R-01            ← 指回需求，每条 R 至少被一个 T 覆盖
    依赖: T-01, T-02      ← 只能指向更小编号，禁止循环
    验证方式: <测试/命令/人工步骤，lint/build 只能兜底不得为唯一>
    验收标准: <可判定的完成条件>
  ```
- 粒度：一个任务一次会话可完成、可独立验证与回滚；总数 3~20，超 20 → 建议拆需求
- **共享面验证规则**：任务触碰共享面（判据见 §3）时，其「验证方式」必须覆盖
  plan 身份矩阵的**每个既有身份各一条断言**——缺矩阵内任一身份的断言
  = 验证方式不合格，确认③不得通过
- 禁止占位任务（「待定」「TODO」「添加适当的错误处理」= 计划缺陷）
- **自检**：每条 R 都有 T 覆盖吗？有 T 找不到对应 R 吗（超范围）？

**门控**：确认③ → 落盘 → **三重确认自检**（读三份版本头，全部已确认+确认人非空）→
通过后先跑**建树五查**（parallel.md 纪律⓪，全绿才许建树）：
①挂接已落账 ②账房 `git status` 空 ③账房 HEAD 在版本分支 ④profile §worktree兼容 非空
（空→先做演练）⑤changelog 权威副本指针行已写。然后在账房建树：
`git worktree add <父目录>/wt-<功能名> -b feature/<功能名> <在途版本分支>`
→ 进入 Phase 4，此后一切工作在该 worktree 内；**文档权威副本在树内，主目录副本=滞后快照**。
完工合并回版本分支按纪律③五步「先入后出→合回→落账→回归→收尾」执行；全程全局账只写碎片

## 5. Phase 4 — Implement

**开工前加载规范**（按 `.specrc.yml` 路由，必然加载）：`code-backend` / `code-frontend` 领域的声明源（按改动内容选一或都选）+ `git-workflow` 领域的 commit 节。

**规范裁决**：`.specrc.yml` 的 `project_files`（AGENTS.md 等）永远最高；其余按各领域声明的源执行；某领域声明为 `global` 时才读本 skill 的 standards/；声明 `none` 则跟随所在文件周边风格。冲突细则见 standards/README.md。

逐任务执行（按依赖序）：
1. 读任务 + 关联的 R 条款 + plan 相关节
2. 最小改动实现；注释解释「为什么」，单次使用的简单逻辑不抽象
3. 跑任务标注的验证方式，**保留真实输出**
4. 勾选 `- [x] T-xx`（勾选不升版本——进度不是内容）
5. commit：`<type>(<scope>): <中文描述≤50字>` + footer `Spec: specs/<目录> vX.Y.Z` 和 `Task: T-xx`（修 bug 的 commit 加 `Bug: BUG-xx`）
6. 每完成一组任务向用户简报：完成项、验证输出、下一步
7. **过程中发现 bug 随手登记**（见下方登记义务表）——不等收尾，发现即写入 `specs/_project/bugs.md`

**共享面提交纪律**（防「修 A 死 B」）：触碰共享面的 commit，**body 必须同时贴两类
实测输出——「改好了」（目标断言）+「没改坏」（身份矩阵中每个既有身份的对面断言）**；
只有前者证据 = 不得提交。改 A 完成 := A 修好 + A 所在共享面的每个身份仍活着，
且两者都有落盘证据（口头声称不算）。

**过程中 Bug 登记义务**（列表完整性靠它，细则 references/bugs.md）：

| 场景 | 动作 |
|---|---|
| 发现**既有代码**的 bug（非本次引入） | 登记 `BUG-xx` 状态「新建」；**不顺手修**（同技术债纪律），除非它阻塞本需求 |
| **对话中**用户提到异常/问题 | 登记（哪怕未确认是否算 bug，状态「新建」待评严重度） |
| **直接修掉的小 bug**（走 NOT for 快速路径） | **强制补登记**——一行流水账换列表完整，修完状态「已修复(vX.Y.Z)」 |
| 我自己实现中验证不过 | **不算 bug 登记**——那是任务未完成，走 completion.md，别混淆 |

**踩坑随手记义务**（lessons.md，与 bug 登记并列的独立义务，细则 references/lessons.md）：
**产品代码行为错**记 bugs.md；**过程/工具/环境/判断上栽的跟头**（含误判、假阳性、白折腾的时间）
记 `specs/_project/lessons.md`——L-xx 永久编号，**当场记不等收尾**；条目必须含可执行的
「防再犯规则」，写不出的不配进台账。被用户纠正的错误必记（同一坑不栽第二次是台账的最低 KPI）。

**并行模式账入口径**：bugs.md/lessons.md/version.md/profile/AGENTS.md 是全局账，
feature worktree 里**只写碎片不写正账**——碎片记在 spec changelog「台账碎片」节
（内容全齐只差编号），合并回版本分支那一刻由账房统一落账编号（parallel.md 纪律②③）。

**待办随手记义务**：用户提到「以后要做/先不做/将来考虑/记一下」→ 当场在
`specs/_project/backlog.md` 记一行 BL（来源写清谁何时）——意向的命比会话上下文长，
忘了记就等于丢（细则 §13）。

全部任务完成后汇报：任务清单勾选状态、各项验证证据、是否满足合并条件
（合并流程见 standards/git-workflow.md §合并）。

**Implement 收尾附加四件事**（与汇报同轮完成）：
1. **生成完成清单** `specs/{目录}/completion.md`（模板见 references/templates.md）：
   已完成项（T-xx + 验证证据 + commit）；未完成项**必须**写原因分类
   （技术阻塞/依赖未就绪/需求变更/主动延期/验证不通过）+ 处置去向（延期→里程碑/移出另立 spec/放弃），
   并在 tasks.md 未勾项同步标注「（延期→vX.Y.Z，原因:…）」——不勾选、不删除、注明去向。
   未经用户批准的「假装完成」是铁律级违规。
2. **升级件登记**：若本 spec 产生了库表/配置变更 → 创建/更新 `specs/{目录}/artifacts.md`
   （格式见 references/milestone.md §四）。纯代码需求不创建。
3. **Bug 核对**：本过程中发现的 bug 是否都已登记；本需求修复的 bug 状态是否已翻「已修复(目标版本)」。
4. **挂接一致性核对**：版本已在 §1 步骤 3 的启动问询时定——此处只核对不提问：
   所挂版本的 MILESTONE.md 需求表确有本 spec 行且状态与实际一致；completion.md 若有
   「延期→vX.Y.Z」项，同步在该版 MILESTONE 表加行/备注（含未勾任务去向）；
   发现改挂未同步台账的，当场补。

**发版时**：走里程碑流程（§9），项目根 CHANGELOG.md 条目从 MILESTONE.md 升级项表生成。

## 6. 版本号规则（摘要，细则必读 standards/versioning.md）

- 版本头格式：`> 版本: v1.0.0 | 状态: 已确认 | 更新: YYYY-MM-DD | 确认人: xxx`
- v0.x = 草稿期；三文档首次全确认 = v1.0.0
- MAJOR = 删需求/改范围/方向推翻（触发重审）；MINOR = 新增条款；PATCH = 措辞澄清
- 目录级统一版本：三个文档共用一个版本序列，changelog.md 集中记到编号级

## 7. 断点续传与异常处理

- 用户说「继续 <功能名>」→ 扫目录：定位第一个状态非「已确认」的文档从对应 Phase 续做；
  三份全确认 → 按 tasks.md 未勾选项继续 Implement；续做前先简报当前位置，等用户确认。
- 需求太模糊 → 追问澄清，不臆测生成。
- 用户要求跳过某阶段 → 说明风险，用户明确坚持才可跳，changelog 记录该决定及原因。
- 无法写 specs/（权限等）→ 告知并暂停。
- 目录已存在同名 → 见 §1.2，先问再动。

**加载任何规范前先查项目根 `.specrc.yml`**：每个领域声明了什么源，就读什么源；
声明 `global`（或无 .specrc.yml 时的默认）才读下表的本 skill 内置文件。
路由语法、探测顺序、裁决细则、完整示例见 `references/standards-routing.md`。

| 领域键（.specrc.yml） | global 源（本 skill 内置） | 何时加载 |

| （索引与裁决规则） | standards/README.md | 首次使用本 skill 时 |

## 9. 里程碑与发版（概要，细则必读 references/milestone.md）

多个需求汇总成一个大版本时启用；不启用里程碑的项目对本节零感知。

```
M0 立项   「新建里程碑 vX.Y.Z」 → releases/vX.Y.Z/ + MILESTONE.md
M1 挂接   启动版本问句拍板即挂（§1.3）；补挂/转挂口令同构。一个 spec 只属一个版本；
          台账表可能被漏记，**事实源 = 本版提交 Spec: footer + spec 目录「挂载:」行**（M3 步骤0 对账）
M2 冻结   「冻结 vX.Y.Z」 → 前置检查（所有 spec 已合并、任务全勾、证据齐）；
          冻结后新需求默认进下一版本，挤入需用户明确同意
M3 汇总   「汇总 vX.Y.Z」 → **步骤0 spec挂接对账（防漏挂，账不平不前进）**
          → 收集各 spec 的 artifacts.md（git log 交叉核对防漏）
          → SQL 合并重排编号（Flyway 风格 V<版本>_<序号>__<描述>.sql + rollback 配对）
          → config/changes.md → RELEASE-NOTES.md（升级项从 R 条款聚合）
          → UPGRADE.md（部署顺序/SQL 顺序/配置/验证/回滚）
M4 发布   「发版 vX.Y.Z」 → 自动审计基线全绿 → checklist 真演练 → **落账批处理（MILESTONE
          翻终态/bugs 翻已发布/CHANGELOG）→ 四步核验（逐条 grep 回验+审计复跑+工作树干净）
          → 才打 tag（账先 tag 后，tag 后修账=事故上账）→ 问合 main（diff 为空验证）→ 问 push（远端复核）**
```

铁律延伸：**M3 未汇总完不得进 M4；checklist 演练项未真做不得打 tag；
**账不齐不打 tag**——发版落账必须在打 tag 前完成并通过四步核验，tag 之后修账 = 事故，
必须记 MILESTONE 审计节并回炉（tag 是历史凭证，它锁住的必须是最终态）；
agent 永不自主合 main、永不自主 push、永不自主回退（三者只问不做——回退仅由用户口令发起）；
悬空期禁止从 main 拉包冒充新版内容。**
升级件（SQL/配置）只在 M3 按版本整理，禁止单需求完成时私自往 releases/ 塞散件。

## 10. init —— 存量项目接入（概要，细则必读 references/init.md）

触发：「初始化 spec / spec init / 接入 spec 机制」。一次跑完约 10 分钟。

```
I1 安全快照    git 状态确认 + 将触碰路径的 sha256 快照
I2 项目体检    只读扫描 7 类事实（技术栈/模块/既有约定/规范skill/git现状/SQL目录/CI）
I3 测试基线    ⚠️ 默认不跑——先问用户「是否运行测试基线？」；
               跑 → 如实记录绿/红与既有失败清单；不跑 → profile 标注「基线未测」
I4 项目画像    生成 specs/_project/profile.md → 用户核对事实
I5 规范路由    生成 .specrc.yml 草稿（I2 发现直接喂入）→ 用户逐行确认
I6 骨架落地    建 specs/；AGENTS.md 无→写入 / 有→备份+追加（展示后确认）
I7 完成报告    装了什么、profile 在哪、建议的第一个 change、声明未碰任何源码
```

**init 铁律**：
1. **只读 + 只新增**——唯一触碰既有文件的是 AGENTS.md（备份+追加，先展示后写）；
   结束后用 I1 快照复验零破坏。
2. **不回填**——不把存量代码反推成 specs（官方与实测共识：back-fill 的 spec 会腐烂）。
   specs 只为将要改动的部分写。
3. **幂等**——重复跑 init 只刷新 profile 的事实与基线段；`.specrc.yml` 已存在则不动（手工改）。
4. **releases/ 延迟创建**——首次「新建里程碑」时才建。

**可选子流程 baseline-capture**（「给 <模块> 建 spec 基线」）：对高风险且即将大改的
单个模块捕获现状规格，一次只做一个，默认不建议——细则见 references/init.md §五。

## 11. Bug 管理（概要，细则必读 references/bugs.md）

项目级唯一清单 `specs/_project/bugs.md`（与 profile.md 并列）。要点：

- 编号 `BUG-xx` 永久不复用；**状态必须绑版本**：
  `新建 → 已规划(vX.Y.Z) → 已修复(vX.Y.Z) → 已验证(vX.Y.Z) → 已发布(vX.Y.Z)`，
  分支状态：`已延期(从vA移至vB)`、`不修复(原因+批准人)`——**不修复必须用户批准，agent 不得自行决定**。
- 登记义务见 §5 表；修 bug 的 commit footer 必带 `Bug: BUG-xx`。
- 修复分级：小 bug（原因明确单点）→ 说「修 BUG-xx」直接修；大 bug（跨模块/需求缺陷）→
  升级建 `fix-xxx` spec 走完整四阶段。
- 里程碑联动：M2 冻结检查本版本「已规划」的 P0/P1 必须达「已验证」；
  RELEASE-NOTES 的「修复」节从 bugs.md 生成；M4 发版把本版本「已验证」批量翻「已发布」。

## 12. 并行模型（本 skill 核心，细则必读 references/parallel.md）

```
启动步骤0: spec_engine 互斥检查（已声明≠自身→拒执；缺失视为自身）
一个活跃 spec = 一个 worktree = 一条 feature 分支；主目录恒检出版本分支 = 账房
全局账唯一通道 = 碎片(append-only, owner 自提) → 落账(账房锁串行, 编号+空间凭证+指纹同点发放)
漂移=硬停(⚑指针+sha256 勾选归一化)；预检脚本三处跑(确认②/落账/M3)；合并回归必含值唯一性断言
跨版本并行禁止；互相独立才可并行（依赖即串行）；软上限 2
```

六纪律 ⓪建树五查 ①物理 ②账 ③合并五步（先入后出→合回→落账→全量回归→remove/回执）
④环境（.accept 双写+占用表核查+schema-per-spec+harness 默认非私库+known-failures 版本级
基线与覆盖缺口 owner+环境快照时间戳广播）⑤互知（兄弟+锁+碎片数）。
配套：行为账 behavior.md（整节替换）；独立评审条件触发；轻确认三行式先呈报后记录。
单人 = 兄弟清单为空的退化情形，同拓扑无特例。

## 13. 待办台账（backlog.md——与版本无关的意向账）

项目级唯一清单 `specs/_project/backlog.md`（与 bugs/version/lessons 同家，首次记录时创建）。
一行式账目：`BL-xx｜标题｜意图｜来源(谁/何时/场合)｜优先级 P0-P3(允许P?)｜状态｜去向`。
状态机：`待办 → 已立项(注 spec 目录) → 已交付(vX.Y.Z) / 已放弃(原因+拍板人)`；
编号永久不复用；放弃行留账不删（防重提时无法考古）。

- **随手记义务**：对话中出现「以后要做/先不做/将来考虑/这个记一下」类意图 → **当场记一行 BL**；
  spec Non-goals 里「以后可能做」的条目收尾时转 BL；completion.md「主动延期」无版本承接的落 BL。
- **口令**：「记录待办 xxx」（新增，回读编号+行）/「待办列表」（只读回显，按优先级排序）/
  「立项 BL-xx」（进 §1 Phase 0，BL 翻已立项注 spec 目录，其「立项前必答」带入 requirements
  待确认问题区）/「放弃 BL-xx」（必须你给原因，agent 不得自行放弃）。
- **边界**：缺陷延期走 bugs 的「待挂版/已延期」态，**不进 BL**——BL 只收新需求意向。
- 联动（**状态同步三锚点**，治「做完了还挂待办」）：
  ① **立项/挂接时**：启动版本问句同轮**反查** backlog 全部「待办」行的意图（标题/域关键词），
     命中 → 摘要带一行「本需求疑似对应 BL-xx（<标题>）——关联吗？」，你说是 → 翻「已立项」注 spec 目录；
     说不是 → 该行加「≠BL-xx」防下轮重复问。**agent 永不静默关联**（合账需授权，同落账纪律）。
  ② **spec 合并落账时**（parallel=合并五步3；单线程=Implement 收尾）：联动检查本 spec 对应 BL——
     仍「待办」即纠错翻「已立项」（防止当初走了"新需求"直立项没关联）；
     **已合并未发版** → 停「已立项（随 vX.Y.Z 待发布）」，**不算已交付**。
  ③ **M4 发版**：本版发布的 BL 才翻「已交付(vX.Y.Z)」；里程碑审计含 BL 互核（滞后行=差异报出）。
- 口令「**待办同步**」：只读三查对账（backlog 各行 vs specs/ 目录状态 vs MILESTONE vs git tag）→
  产出纠正清单（该翻/滞后/无去向/≠误关联）逐条经你确认后才写账——存量滞后账用它一次性治平。
模板见 references/templates.md。
